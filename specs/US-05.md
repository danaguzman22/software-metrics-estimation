## Fuente única de requisitos

>
> Criterios de aceptación:
> - CA1. Cada ítem tiene ID, título, descripción, prioridad, estado, story points y criterios de aceptación.

> - CA3. Título vacío o prioridad inválida devuelve error.

Esta spec no agrega requisitos fuera de esa fuente. Las decisiones confirmadas por la persona se transcriben en la sección 12 y se aplican en todo el documento; no quedan decisiones abiertas. ## 1. Objetivo

Permitir que un Product Owner cree ítems del Product Backlog en un proyecto **existente** identificado por su ID (D1), con título, descripción, prioridad y criterios de aceptación, para organizar el trabajo del proyecto. El alta asigna automáticamente un ID único dentro del proyecto (D3), fija el estado inicial "Pendiente" (D6) y deja los story points en 0 (D7); no recibe ni permite elegir esos valores.

El alcance de esta historia es el alta de ítems del backlog, sus validaciones, el error de proyecto inexistente y la persistencia del alta en la capa de servicio. No incluye editar ni reordenar ítems (US-06), asignarlos a un Sprint (US-08), estimarlos con la escala Fibonacci (US-11) ni interfaz web (D12).

## 2. Entradas

| Entrada | Descripción | Origen del requisito |

| ID del proyecto | Identificador del proyecto existente al que se agrega el ítem. El proyecto se identifica por su ID y la existencia se verifica en la capa de servicio buscando el ID en la colección `"proyectos"` persistida. | Título | Título del ítem. No puede estar vacío ni compuesto únicamente por espacios; se valida y se guarda sin espacios al inicio y al final (D4). Se recibe como `titulo string` en `domain.NuevoItemBacklog` (D10) y en `CrearItem` (D11). | CA1, CA3, D4 |
| Descripción | Descripción del ítem. Es opcional, texto libre y no se valida (D8). Se recibe como `descripcion string`. | CA1, D8 |
| Prioridad | Prioridad del ítem. Solo se aceptan los valores exactos `"Alta"`, `"Media"` o `"Baja"`, evaluados después de recortar espacios al inicio y al final; cualquier otro valor es error (D5). Se recibe como `prioridad string`. | CA1, CA3, D5 |
| Criterios de aceptación | Lista de criterios de aceptación del ítem. Es opcional, texto libre y no se valida (D8). Se recibe como `criterios []string`. | CA1, D8 |

El alta **no recibe** ID, estado ni story points: el ID se genera automáticamente en el servicio (D3), el estado inicial siempre es "Pendiente" (D6) y los story points quedan en 0 (D7). La historia no define campos adicionales del ítem.

## 3. Salidas esperadas

| Situación | Salida esperada |
|---|---|
| Alta válida | El ítem queda registrado en la colección `"backlog"` del proyecto, junto a los que ya tenga, con su ID generado, título recortado, descripción, prioridad recortada, estado "Pendiente", story points 0 y criterios de aceptación. La operación devuelve el ítem agregado como `domain.ItemBacklog` (D10, D11). |
| Título vacío o compuesto solo por espacios | `domain.ErrTituloItemVacio` (D10). El ítem no queda registrado y la operación devuelve `domain.ItemBacklog{}`. |
| Prioridad inválida | `domain.ErrPrioridadInvalida` (D10). El ítem no queda registrado y la operación devuelve `domain.ItemBacklog{}`. |
| Proyecto inexistente | `domain.ErrProyectoNoEncontrado`. El ítem no queda registrado y la operación devuelve `domain.ItemBacklog{}`. |
| Varios errores a la vez | Se devuelve el primer error aplicable según el orden decidido (D9): 1) proyecto inexistente, 2) título vacío, 3) prioridad inválida. |
| Error de almacenamiento | El error se propaga envuelto (`fmt.Errorf` con `%w`), sin mapearse a no-encontrado (D2). No se informa alta exitosa y la operación devuelve `domain.ItemBacklog{}`. |

Notas de interpretación (derivadas de las decisiones confirmadas; no agregan requisitos):

- **R2 / ID (D3):** el ID no forma parte de las entradas ni de `domain.NuevoItemBacklog`; lo asigna el servicio porque depende de los ítems ya existentes en el proyecto. La numeración es independiente por proyecto. El ancho del ID para más de 99 ítems no está definido en las decisiones y se lista al final como pendiente.
- **R3 / título (D4):** "vacío" incluye el compuesto únicamente por espacios. El recorte se aplica antes de validar y es la forma que se guarda.
- **R4 / prioridad (D5):** la comparación es exacta y distingue mayúsculas después de recortar espacios; `"alta"` no es válido. El valor válido se guarda recortado.
- **R6 / estado (D6):** el alta no recibe el estado; "Pendiente" es el único estado por ahora y no se valida desde la entrada.
- **R7 / story points (D7):** 0 significa "sin estimar". La estimación y la escala Fibonacci son de US-11.
- **R8 / descripción y criterios (D8):** al ser texto libre sin validar, no se recortan ni se transforman; se almacenan como llegan.
- **R9 / orden (D9):** primero la existencia del proyecto, luego el título y por último la prioridad. Es el mismo precedente de US-02 y US-03 para la existencia del proyecto.
- **R10 / persistencia (D2):** se reutiliza el contrato de US-02 y US-03; la colección `"backlog"` es propia y no se mezcla con `"proyectos"` ni `"integrantes"`.

## 5. Restricciones

- El actor es el Product Owner; no se definen roles de usuario, permisos ni autenticación.
- El ítem se crea con título, descripción, prioridad y criterios de aceptación, según la historia y CA1; el ID, el estado y los story points los fija el sistema (D3, D6, D7). No se agregan campos adicionales.
- El proyecto se identifica por ID (D1); no se usa el nombre del proyecto como identificador.
- La persistencia vive en la capa de servicio sobre el contrato mínimo de almacenamiento (`Save`/`Load`), satisfecho por `*storage.JSONStore`; no se modifica T-02 ni `internal/storage` (D2). Los ítems se guardan en una colección propia `"backlog"` (archivo `backlog.json`) con registros `{ProyectoID, Item}`; no se modifica `domain.Proyecto`, ni la colección `"proyectos"`, ni T-02, ni los tests de US-01, US-02 y US-03 (D2).
- La lógica de negocio vive en `internal/domain`: tipo `domain.ItemBacklog` y constructor `domain.NuevoItemBacklog` (D10). La capa web no duplica reglas. Esta historia no tiene capa web (D12).
- El caso de uso vive en un servicio nuevo `ServicioBacklog`, en un archivo nuevo `internal/service/backlog.go`, con el método `CrearItem` (D11). No se modifica `ServicioProyectos` ni sus archivos.
- Los errores nuevos son `domain.ErrTituloItemVacio` y `domain.ErrPrioridadInvalida` (D10). El error `domain.ErrProyectoNoEncontrado` se reutiliza tal como existe (D1).
- Fuera de alcance (D12): editar o reordenar ítems (US-06), asignar a Sprint (US-08), estimar con Fibonacci (US-11) e interfaz web. Tampoco listado o consulta de ítems ni operaciones no mencionadas por la historia.

## 6. Casos límite

- Primer ítem de un proyecto sin ítems: recibe `"HU-01"` (R2).
- Proyecto con ítems `"HU-01"` y `"HU-03"`: el siguiente ítem recibe `"HU-04"`; no se rellenan huecos (R2).
- Dos altas consecutivas en el mismo proyecto: IDs distintos y consecutivos (`"HU-01"`, `"HU-02"`) (R2).
- Ítems de otros proyectos: no afectan la numeración del proyecto actual; el primer ítem de otro proyecto también recibe `"HU-01"` (R2).
- Título compuesto únicamente por espacios: es vacío; `domain.ErrTituloItemVacio` (R3).
- Título con espacios externos y contenido (`"  Registrar proyecto  "`): válido; se guarda como `"Registrar proyecto"` (R3).
- Prioridad con espacios externos (`"  Alta  "`): válida; se guarda como `"Alta"` (R4).
- Prioridad con diferencia de mayúsculas (`"alta"`, `"ALTA"`): inválida; `domain.ErrPrioridadInvalida` (R4).
- Prioridad compuesta únicamente por espacios (`"   "`): inválida; `domain.ErrPrioridadInvalida` (R4).
- Descripción vacía y criterios ausentes o lista vacía: válidos; el alta es exitosa (R8).
- Descripción o criterios con texto libre (acentos, signos, espacios): válidos; no se validan ni se transforman (R8).
- Título repetido en el mismo proyecto: permitido; no se valida unicidad (R3, D4).
- Archivo de la colección `"proyectos"` inexistente: se interpreta como colección vacía y el proyecto no se encuentra (R5, D2).
- Archivo de la colección `"backlog"` inexistente: se interpreta como backlog vacío; la primera alta es exitosa y crea la colección (R1, R10).
- Backlog con ítems de otros proyectos: se conservan y no participan en el cálculo del ID del proyecto actual (R2, R10).
- Cantidad máxima de ítems por proyecto: no definida por la historia ni por las decisiones; no se valida.
- ID para más de 99 ítems en un proyecto: el formato no está definido en las decisiones; se lista como pendiente al final.

## 11. Contrato de identificación y persistencia

US-05 necesita identificar el proyecto al que se agrega el ítem, generar el ID y persistir el alta. El mecanismo genérico de persistencia ya existe (`internal/storage.JSONStore` con `Save` y `Load`, errores `storage.ErrNotFound`, `storage.ErrCorrupt` y `storage.ErrInvalidName`, escritura atómica) y no se modifica (D2).

**Estado: modelo y contrato confirmados por decisión de la persona (D1–D3, D10, D11).**

Qué está decidido:

- **Persistencia (D2):** colección propia `"backlog"` (archivo `backlog.json`) con registros `{ProyectoID, Item}`. `storage.ErrNotFound` implica colección vacía; los demás errores se envuelven con `%w` y no se mapean a no-encontrado. No se modifica T-02, `internal/storage`, `domain.Proyecto`, la colección `"proyectos"` ni los tests de US-01, US-02 y US-03.
- **Dominio (D10):** tipo `domain.ItemBacklog` con los campos de CA1 (ID, título, descripción, prioridad, estado, story points y criterios de aceptación); constructor `NuevoItemBacklog(titulo, descripcion, prioridad string, criterios []string) (ItemBacklog, error)` que valida título y prioridad y fija el estado `"Pendiente"` y los story points 0; errores `ErrTituloItemVacio` y `ErrPrioridadInvalida`.
- **Caso de uso (D11):** método de `ServicioBacklog`: `CrearItem(proyectoID, titulo, descripcion, prioridad string, criterios []string) (domain.ItemBacklog, error)`, en un archivo nuevo `internal/service/backlog.go`. Devuelve el ítem agregado y `domain.ItemBacklog{}` ante error.
- **ID (D3):** se genera en el servicio, porque depende de los ítems existentes del proyecto; no lo recibe el constructor de dominio.

Flujo del caso de uso (orquestación en el servicio; coherente con el orden decidido en D9):

1. `Load("proyectos", &coleccion)`: si devuelve `storage.ErrNotFound`, se interpreta como colección vacía (contrato de US-02 y US-03, D2).
2. Buscar el proyecto por ID: si no está, se devuelve `domain.ErrProyectoNoEncontrado` (D1). Esta verificación va primero (D9).
3. Validar título y prioridad con `domain.NuevoItemBacklog(titulo, descripcion, prioridad, criterios)` (D4, D5, D8, D10) en el orden decidido (D9): título, luego prioridad. Si falla, se devuelve el error sin escribir nada.
4. `Load("backlog", ...)`: si devuelve `storage.ErrNotFound`, se interpreta como colección vacía (primera alta); cualquier otro error se propaga envuelto (D2).
5. Calcular el siguiente ID del proyecto según R2 (mayor existente de ese `ProyectoID` más uno; `"HU-01"` si no hay ítems) y asignarlo al ítem.
6. Agregar el registro `{ProyectoID, Item}` a la colección `"backlog"` y `Save("backlog", ...)` (D2). Si `Save` falla, el error se propaga envuelto y no se informa alta exitosa; por la escritura atómica de T-02, el archivo conserva el contenido previo.
7. Devolver el `domain.ItemBacklog` creado.

Los tests sembrarán el almacenamiento mediante `JSONStore` (como en US-02 y US-03): la colección `"proyectos"` para el proyecto destino y la colección `"backlog"` para los ítems previos. US-05 no incluye la operación de crear proyectos persistidos ni de asignar IDs de proyecto.
