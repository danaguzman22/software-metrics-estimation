## 1. Objetivo

Mudar la regla "el siguiente ID de ítem es el mayor número existente del proyecto más uno" desde la lógica implícita de `internal/service/backlog.go:63-96` (`numeroDeItem`) a dos funciones puras de `internal/domain`:

- `domain.NumeroDeItem(id string) (int, bool)` — extrae el número de un ID con patrón `"HU-NN"`.
- `domain.SiguienteIDItem(idsExistentes []string) string` — devuelve el próximo ID del proyecto.

El objetivo es que **ambos adaptadores de repositorio** (JSON y PostgreSQL) compartan la misma regla (ADR-001 D4) y que `CrearItem` la use, **sin cambiar el comportamiento observable** de la creación de ítems. La regla es de dominio, no de persistencia ni de interfaz: esta tarea no incluye UI, almacenamiento, migraciones ni cambios de requisitos. La lógica nueva vive en `internal/domain/numeracion_item.go` y su test en `internal/domain/numeracion_item_test.go` (P7).

## 2. Entradas

| Entrada | Tipo | Descripción | Origen del requisito |
|---|---|---|---|
| IDs existentes | `idsExistentes []string` | IDs de los ítems ya existentes **del proyecto** para el que se calcula el siguiente. El llamador los filtra por proyecto: la función no conoce proyectos (P9). Puede ser una lista vacía o `nil`; ambas se comportan igual (R3, P5). Los IDs malformados se ignoran (R7). | Issue #39 (firma), ADR-001 D4, P5, P9 |
| ID de ítem | `id string` | ID a interpretar con el patrón `"HU-NN"`, por ejemplo `"HU-01"`, `"HU-9"`, `"HU-001"`, `"HU-04"` o `"HU-100"`. El sufijo debe ser solo dígitos ASCII `0-9` con valor mayor o igual a 1 (R1, R2). | Issue #39 (firma), ADR-001 D4, P1–P4, P6 |

`SiguienteIDItem` **no recibe** el ID del proyecto, el backlog completo ni los ítems del dominio: solo recibe la lista de IDs ya filtrada por el llamador (P9). `NumeroDeItem` no recibe configuración, ancho ni prefijo: el prefijo y el formato son fijos (R1, R4).

## 3. Salidas esperadas

| Situación | Salida esperada |
|---|---|
| `SiguienteIDItem` con lista vacía o `nil` | `"HU-01"` (R3, P5). |
| `SiguienteIDItem` con lista sin ningún ID válido (todos malformados) | `"HU-01"` (R3, R7). |
| `SiguienteIDItem` con IDs válidos | El mayor número existente más uno, con formato `"HU-%02d"`: `"HU-01"`, `"HU-04"`, `"HU-100"`, `"HU-101"` (R4, R8). |
| `SiguienteIDItem` con huecos en la secuencia | Toma el máximo numérico más uno; **no rellena huecos** (R5). |
| `SiguienteIDItem` con IDs de distinto ancho (`"HU-9"`, `"HU-10"`) | Compara números, no texto: devuelve `"HU-11"` (R6). |
| `NumeroDeItem` con ID válido | `(número, true)`: `"HU-01"` → `(1, true)`, `"HU-100"` → `(100, true)`, `"HU-9"` → `(9, true)`, `"HU-001"` → `(1, true)` (R1, P1, P2). |
| `NumeroDeItem` con ID inválido | `(0, false)`: prefijo incorrecto, string vacío, prefijo sin número, signos (`"HU--1"`, `"HU-+1"`), valor `0` (`"HU-0"`, `"HU-00"`) u overflow (R2, P3, P4, P6). |
| Cualquier entrada | Las funciones no devuelven `error`, no hacen I/O, no usan estado global y no mutan `idsExistentes` (R9). `SiguienteIDItem` siempre devuelve un ID con formato válido. |

Notas de interpretación (derivadas del issue, de ADR-001 D4 y de las decisiones P1–P9; no agregan requisitos):

- **R1 / patrón (D2, P1–P4, P6):** el patrón es prefijo `"HU-"` exacto más un sufijo de solo dígitos ASCII `0-9`. Se aceptan números sin cero a la izquierda (`"HU-9"`, P1) y con ceros a la izquierda (`"HU-001"`, P2). No se aceptan signos (`"HU--1"`, `"HU-+1"`, P4), valor `0` (`"HU-0"`, `"HU-00"`, P3) ni overflow (P6). La validación es explícita carácter por carácter porque `strconv.Atoi` acepta signos.
- **R3, R4 / máximo (D2, D4, P5):** el resultado es siempre `máximo + 1`; el máximo se calcula solo con IDs válidos. Una lista vacía, `nil` o sin IDs válidos equivale a máximo 0 → `"HU-01"`.
- **R6 / comparación (D4):** se compara el número extraído, no el string. `"HU-10"` es mayor que `"HU-9"` aunque textualmente `"HU-9"` sea mayor.
- **R7 / malformados (D4, P6):** "ignorar" significa no participar del máximo; no es un error ni detiene el cálculo. Un sufijo con overflow también se ignora.
- **R10 / delegación (issue CA5, ADR-001 sección 6 paso 1, P9):** el servicio sigue verificando el proyecto, validando el ítem y persistiendo igual que hoy; solo cambia de dónde sale la regla de numeración. El llamador filtra los IDs por proyecto.
- **R11 / alcance (ADR-001 D4, P7, P8):** la función es de dominio y la comparten los adaptadores; esta tarea no implementa adaptadores ni persistencia. `numeroDeItem` se elimina si no tiene más usos o queda como wrapper fino.

## 5. Restricciones

- **Funciones puras de dominio.** Viven en `internal/domain` y no conocen persistencia, HTTP, templates ni proyectos. No hacen I/O, no usan estado global y no mutan la entrada (R9). Una lista `nil` se trata igual que una vacía (P5).
- **Validación explícita del sufijo.** El sufijo se valida carácter por carácter como dígitos ASCII `0-9`; no se usa `strconv.Atoi` como única validación porque acepta `"+1"` y `"-1"` (P4). El valor debe ser mayor o igual a 1 (P3) y el overflow es inválido (P6).
- **Sin UI.** T-05 no tiene capa web ni comportamiento de usuario. Por eso **no existe `features/T-05.feature`** y no se crea en esta tarea.
- **Sin cambio de comportamiento.** `CrearItem` debe producir exactamente los mismos IDs que hoy para el mismo backlog. Los tests existentes de US-05 deben seguir pasando sin cambios (R10, R11).
- **Sin cambios en persistencia.** No se modifica `internal/storage`, no se crean adaptadores, no se tocan migraciones ni PostgreSQL. El adaptador JSON y el de PostgreSQL usarán estas funciones en tareas posteriores (ADR-001 D4).
- **Sin errores nuevos.** Las funciones no devuelven `error`; un ID inválido (incluidos signos, valor `0` y overflow) es `(0, false)` y un ID malformado en la lista se ignora. No se agregan errores de dominio.
- **Firmas exactas.** Se respetan las firmas decididas en ADR-001 D4 y sección 11: `SiguienteIDItem(idsExistentes []string) string` y `NumeroDeItem(id string) (int, bool)`.
- **Alcance acotado.** No se modifican las specs ni los `.feature` existentes, ni `domain.Proyecto`, ni las firmas públicas de los métodos de servicio. La lógica nueva vive solo en `internal/domain/numeracion_item.go` (P7); `internal/service/backlog.go` se limita a delegar. `numeroDeItem` se elimina si no tiene más usos o queda como wrapper fino (P8).
- **TDD.** Los tests nuevos se escriben primero en RED y luego el código en GREEN; `go test ./...` debe quedar en verde (issue #39).

## 6. Casos límite

- Lista vacía: `"HU-01"` (R3).
- Lista `nil` (`var ids []string`): se trata igual que una lista vacía → `"HU-01"` (R3, P5).
- Lista con un solo ID: `["HU-01"]` → `"HU-02"` (R4).
- Secuencia completa `"HU-01"`..`"HU-03"`: `"HU-04"` (R4).
- Hueco `["HU-01", "HU-03"]`: `"HU-04"`; no se rellena `"HU-02"` (R5).
- Lista con IDs malformados mezclados: se ignoran y el resultado es el mismo que sin ellos (R7).
- Lista con **solo** IDs malformados: `"HU-01"` (R3, R7).
- Comparación numérica `["HU-9", "HU-10"]`: `"HU-11"` (R6).
- Orden de la lista irrelevante: `["HU-03", "HU-01"]` → `"HU-04"` (R4).
- IDs duplicados: `["HU-01", "HU-01"]` → `"HU-02"` (R4).
- Más de 99: `["HU-99"]` → `"HU-100"`; `["HU-100"]` → `"HU-101"` (R8).
- `NumeroDeItem` con string vacío: `(0, false)` (R2).
- `NumeroDeItem` con prefijo correcto y sin número (`"HU-"`): `(0, false)` (R2).
- `NumeroDeItem` con prefijo incorrecto (`"XX-01"`) o distinta capitalización (`"hu-01"`): `(0, false)` (R2).
- `NumeroDeItem` con espacios externos (`" HU-01"`, `"HU-01 "`): `(0, false)` (R2).
- `NumeroDeItem("HU-9")`: `(9, true)`; se aceptan números sin cero a la izquierda (R1, P1).
- `NumeroDeItem("HU-001")`: `(1, true)`; se aceptan ceros a la izquierda y el valor es 1 (R1, P2).
- `NumeroDeItem("HU-0")` y `"HU-00"`: `(0, false)`; los números empiezan en 1 (R2, P3).
- `NumeroDeItem("HU--1")`, `"HU-+1"`: `(0, false)`; los signos no son dígitos ASCII (R2, P4).
- Sufijo que excede el rango de `int` (por ejemplo, 30 dígitos): `(0, false)`; en `SiguienteIDItem` se ignora (R2, R7, P6).

## 7. Condiciones de error

Las funciones de T-05 **no devuelven `error`** y no introducen errores de dominio nuevos. Los casos inválidos se expresan con `ok == false` o se ignoran; `SiguienteIDItem` siempre devuelve un ID.

| ID | Condición | Resultado esperado | Regla |
|---|---|---|---|
| E1 | `id` sin el prefijo `"HU-"` o con prefijo distinto (por ejemplo `"XX-01"`, `"hu-01"`). | `NumeroDeItem` devuelve `(0, false)`. No es un error. | R2 |
| E2 | `id` con el prefijo pero sin número interpretable (por ejemplo `""`, `"HU-"`, `"HU-abc"`, `"HU-01x"`). | `NumeroDeItem` devuelve `(0, false)`. No es un error. | R2 |
| E3 | `idsExistentes` contiene IDs malformados. | Se ignoran para el cálculo; si queda al menos un ID válido, se usa el máximo; si no queda ninguno, se devuelve `"HU-01"`. No es un error. | R3, R7 |
| E4 | `idsExistentes` vacía o `nil`. | `"HU-01"`. No es un error. | R3, P5 |
| E5 | `id` con signo (`"HU--1"`, `"HU-+1"`). | `NumeroDeItem` devuelve `(0, false)`. No es un error. | R2, P4 |
| E6 | `id` con valor `0` (`"HU-0"`, `"HU-00"`). | `NumeroDeItem` devuelve `(0, false)`. No es un error. | R2, P3 |
| E7 | `id` con un sufijo que excede el rango de `int` (por ejemplo, 30 dígitos). | `NumeroDeItem` devuelve `(0, false)`; en `SiguienteIDItem` se ignora. No es un error. | R2, R7, P6 |

No se agregan condiciones de error adicionales (por ejemplo, longitud máxima del ID o cantidad máxima de IDs) porque el issue y el ADR no las definen. El parseo ya está cerrado por P1–P6.

## 11. Contrato de las funciones de dominio

Firmas exactas decididas en ADR-001 D4 y sección 11. Archivo: `internal/domain/numeracion_item.go` (P7).

```go
// NumeroDeItem extrae el número de un ID con el patrón "HU-NN".
// El sufijo debe ser solo dígitos ASCII 0-9, con valor mayor o igual a 1.
// Devuelve false si el ID no tiene ese patrón, incluidos signos, valor 0
// y overflow del sufijo.
func NumeroDeItem(id string) (int, bool)

// SiguienteIDItem devuelve el próximo ID de ítem del proyecto:
// "HU-01" si no hay ítems previos (o ninguno con patrón válido) y, si no,
// el mayor número existente más uno, con el formato actual "HU-%02d".
func SiguienteIDItem(idsExistentes []string) string
```

Semántica:

- `NumeroDeItem` devuelve `(0, false)` ante cualquier ID que no cumpla el patrón (R2), incluidos signos (`"HU--1"`, `"HU-+1"`, P4), valor `0` (`"HU-0"`, `"HU-00"`, P3) y overflow (P6). No distingue por qué falló.
- El sufijo se valida explícitamente carácter por carácter como dígito ASCII `0-9`; no se usa `strconv.Atoi` como única validación porque acepta `"+1"` y `"-1"` (P4).
- `SiguienteIDItem` calcula el máximo de los números válidos de `idsExistentes`; si no hay ninguno, o la lista es `nil`, el máximo es 0. Devuelve `fmt.Sprintf("HU-%02d", maximo+1)` (R3, R4, P5).
- El ancho mínimo es 2 y no hay truncamiento: 99 → `"HU-100"`, 100 → `"HU-101"` (R8).
- Las funciones no reciben ni devuelven proyectos: el llamador pasa solo los IDs del proyecto correspondiente (R10, P9).
- Las funciones no devuelven `error` ni modifican la entrada (R9).

Flujo de `CrearItem` (sin cambio de comportamiento, R10):

1. Verificar que el proyecto exista (sin cambios).
2. Validar los datos del ítem con `domain.NuevoItemBacklog` (sin cambios).
3. Cargar la colección `"backlog"` (sin cambios).
4. Recolectar los IDs de los ítems cuyo `ProyectoID` coincide con el proyecto pedido (P9).
5. Llamar a `domain.SiguienteIDItem(idsDelProyecto)` y asignar el resultado a `nuevo.ID` (reemplaza el cálculo inline actual de `internal/service/backlog.go:63-72`).
6. Agregar el registro y guardar (sin cambios).

`internal/service/backlog.go` deja de tener la lógica de numeración. `numeroDeItem` se elimina si no tiene más usos; si algún test existente lo llama directamente, queda como wrapper fino sobre `domain.NumeroDeItem`. La persona debe verificar los usos reales antes de eliminarlo (P8).
