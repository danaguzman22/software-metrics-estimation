## Fuente y decisiones

La fuente es la tarea técnica T-16: "Mejora visual de la interfaz". La persona
decidió el alcance, la dirección visual, las pantallas, las restricciones de
impresión y la forma de verificar. Esta especificación las registra sin
extenderlas. Los detalles no definidos del CSS se proponen como DERIVADOS en
la sección 4; no hay decisiones pendientes.

Referencias de formato y estructura: `specs/T-15.md` y `specs/US-21.md`.
La revisión de implementación incluye `base.html`, todas las plantillas
existentes y `internal/web/estaticos/estilos.css`.

## 1. Objetivo y alcance

Mejorar la presentación visual de todas las pantallas accesibles sin cambiar
su contenido, estructura ni comportamiento.

El único archivo de implementación permitido es
`internal/web/estaticos/estilos.css`. Los archivos `specs/T-16.md` y
`features/T-16.feature` son los artefactos SDD/BDD de esta tarea. No se
modifica ningún otro archivo.

El CSS se aplica al HTML y a las clases existentes. No se agregan ni renombran
clases, no se cambian las plantillas ni las rutas y no se modifica el dominio,
los servicios, la lógica del servidor ni los gráficos SVG.

## 2. Dirección visual decidida

- Fondo general gris muy claro `#f5f7fb`.
- Tarjetas blancas con borde sutil `#e5e9f2`, esquinas redondeadas de
  aproximadamente `12px` y sombra suave.
- Navegación superior azul marino `#0f1f4b`, con texto claro, respetando el
  HTML existente; no se agrega barra lateral.
- Acento principal azul/índigo (`#2563eb` / `#4f46e5`) en botones primarios.
- Verde `#10b981` para estados positivos, violeta `#7c3aed` y naranja
  `#f59e0b` como acentos secundarios; rojo para defectos y alertas.
- Tipografía legible del sistema, con jerarquía clara, espaciado consistente
  y colores expresados mediante variables CSS en `:root`.
- Foco de teclado visible mediante contorno. El significado de estados y
  acciones debe seguir expresado con texto y no depender solo del color.
- Tablas con encabezados diferenciados y bordes de fila suaves.
- Formularios con etiquetas legibles, controles consistentes y errores
  claramente distinguibles.
- Diseño adaptable, con un punto de quiebre móvil en
  `@media (max-width: 640px)`. En pantallas estrechas, las tablas conservan su
  formato tabular y se pueden recorrer horizontalmente desde su contenedor;
  no se usa `display: block` en tablas.

La referencia visual aporta únicamente estilo. No se trasladan funciones,
secciones ni estructuras que no existan en la aplicación.

## 3. Pantallas incluidas

El recorrido y el tratamiento visual cubren cada pantalla accesible existente:

1. Inicio y lista de proyectos.
2. Alta de proyecto y detalle del proyecto.
3. Backlog, alta de ítem, edición de ítem y estimación inline.
4. Planning Poker.
5. Sprints, alta de Sprint e histórico de Sprints.
6. Defectos del proyecto e integrantes.
7. Dashboard.
8. Reporte de proyecto y reporte de Sprint.
9. Páginas de error.

La adaptación se realiza con reglas CSS sobre los elementos y clases actuales,
incluidas `.encabezado`, `.navegacion`, `.contenido`, `.tabla`, `.detalle`,
`.formulario`, `.acciones`, `.en-linea`, `.error`, `.leyenda`, `.grafico`,
`.reporte` y las clases de migas y volver añadidas por T-15. Las tablas sin
clase específica también conservan su presentación tabular y comportamiento
adaptable.

## 4. Decisiones y detalles derivados

El alcance, la paleta, las pantallas y las restricciones enumeradas en esta
spec son **DECIDIDOS**. Para los aspectos de implementación CSS no fijados
por esas decisiones, se proponen estos detalles **DERIVADOS**:

| ID | Detalle derivado |
|---|---|
| D1 | Definir en `:root` variables para colores de superficie, texto, bordes, acentos, estados, foco, sombras, radios y espaciado; reutilizarlas en los selectores existentes. |
| D2 | Agregar al final de `estilos.css` un bloque propio delimitado por comentarios `T-16` de apertura y cierre. Mantener todos los estilos existentes fuera de ese bloque sin cambios y no editar el bloque T-15. |
| D3 | Usar `@media (max-width: 640px)` como punto de quiebre para ajustar navegación, espaciado, formularios y contenedor desplazable de tablas. No cambiar el modelo de tabla a bloques. |
| D4 | Aplicar estilos a elementos HTML y clases ya presentes; cuando una plantilla carezca de una clase de tarjeta, utilizar selectores de elementos o relaciones CSS que no requieran cambios de marcado ni nuevos nombres de clase. |
| D5 | Mantener el foco visible con `:focus-visible` y un contorno de contraste suficiente, sin quitar el indicador de foco del navegador si no se proporciona un reemplazo equivalente. |

Estos detalles concretan el CSS dentro del alcance decidido y no requieren una
decisión adicional.

## 5. Exclusiones

No se implementan ni se simulan:

- Barra lateral, buscador, filtros por período o Sprint, notificaciones ni
  avatar.
- Comparativos "vs. período anterior", sección "novedades", Ayuda o
  Configuración.
- Nuevas funciones, estructura, contenido o controles no presentes en el HTML.
- Cambios de plantillas, marcado, nombres de clase, rutas, handlers, dominio
  o servicios.
- JavaScript nuevo. Se conserva sin cambios el único uso existente de
  `window.print`.
- Librerías, CDN, frameworks CSS/JS o paso de build, incluyendo Tailwind,
  Chart.js, Lucide y HTMX.
- Cambios a los gráficos SVG generados por el servidor.
- Reglas generales de impresión o alteraciones a las reglas existentes de
  `@media print` acotadas a `.reporte`.

## 6. Contrato de comportamiento y accesibilidad

La tarea no cambia el comportamiento HTTP. Las páginas mantienen sus códigos
de respuesta, enlaces, acciones, formularios y contenido existentes. El CSS
continúa sirviéndose desde `/static/estilos.css`.

La presentación mejora sin alterar la semántica: controles siguen siendo
operables, los enlaces y botones conservan estados de interacción visibles,
los errores siguen identificables y la información de estado no se comunica
solo con color.

Todas las reglas actuales de impresión asociadas a `.reporte` se conservan
intactas. La impresión de un reporte mantiene el comportamiento existente,
incluidos encabezados de tabla y ocultamiento de navegación y controles de
impresión.

| Criterio | Resultado verificable | Escenario |
|---|---|---|
| CA1 | La única modificación de implementación es el CSS permitido y las pantallas conservan su estructura y comportamiento. | Las páginas existentes conservan respuestas, enlaces y contenido. |
| CA2 | El CSS servido refleja la dirección visual y adapta la interfaz a escritorio y móvil. | Se sirve la hoja de estilos y se verifica su presentación en ambos anchos. |
| CA3 | Las tablas mantienen el formato tabular y se pueden recorrer horizontalmente en móvil sin `display: block`. | Tabla ancha en viewport móvil. |
| CA4 | Las reglas de impresión de reportes y el bloque de T-15 permanecen intactos. | Imprimir un reporte y comparar los bloques protegidos del CSS. |
| CA5 | No se incorporan funciones o dependencias visuales fuera del alcance. | Inspección del diff de archivos y recursos. |

Los pasos BDD están en `features/T-16.feature`. Como no hay un nuevo
comportamiento HTTP que justifique un ciclo de pruebas RED, no se agrega un
ciclo RED/GREEN/REFACTOR ni se crean tests de servidor para esta tarea.

## 8. Verificación

La verificación comprende:

1. Ejecutar la suite completa existente en verde: `go test ./... -count=1`.
2. Hacer un recorrido visual de todas las pantallas de la sección 3, tanto en
   escritorio como con viewport de hasta `640px`.
3. Confirmar que tablas anchas se recorren horizontalmente, que no aparece
   desplazamiento horizontal inesperado de toda la página y que las tablas no
   cambian a `display: block`.
4. Verificar foco visible, contraste legible, etiquetas y errores en
   formularios, y que los estados siguen comprensibles sin depender del color.
5. Imprimir al menos un reporte y comprobar que las reglas existentes de
   impresión siguen funcionando.
6. Comparar el bloque T-15 y las reglas de impresión con su contenido previo;
   ambos deben conservarse intactos.
7. Revisar el diff para confirmar que no haya cambios de implementación fuera
   de `internal/web/estaticos/estilos.css`, sin nuevos recursos ni dependencias.

La suite automatizada cubre regresiones funcionales; el recorrido visual y la
impresión son verificaciones manuales requeridas porque la tarea es de
presentación.

## 9. Cambios previstos por sección del CSS

| Sección | Cambio previsto |
|---|---|
| Variables y base | Agregar variables visuales en `:root` y aplicar fondo, texto y tipografía del sistema. |
| Navegación y contenido | Actualizar cabecera, enlaces, ancho y espaciado del contenido, sin crear una barra lateral. |
| Superficies y jerarquía | Estilizar tarjetas/secciones existentes, encabezados, leyendas y detalles con bordes, radios y sombras suaves. |
| Acciones y estados | Diferenciar enlaces y botones primarios/secundarios, estados hover/focus y errores; no reemplazar sus etiquetas textuales. |
| Formularios | Mejorar controles, etiquetas, espaciado, validación visual y foco usando los elementos existentes. |
| Tablas y gráficos | Diferenciar encabezados, filas y contenedores; conservar SVG y permitir desplazamiento horizontal de tablas en móvil. |
| Adaptación móvil | Agregar reglas bajo `@media (max-width: 640px)` sin alterar el marcado y sin `display: block` en tablas. |
| T-15 e impresión | Conservar sin edición el bloque delimitado T-15 y las reglas `@media print` de `.reporte`; agregar únicamente el bloque T-16 separado. |

## 10. Riesgos y mitigaciones

| Riesgo | Mitigación |
|---|---|
| Selectores CSS demasiado amplios alteran pantallas no previstas. | Reutilizar clases y elementos encontrados en las plantillas; recorrer todas las pantallas y revisar diffs. |
| Tablas amplias desbordan el viewport móvil. | Hacer desplazable horizontalmente el contenedor existente; mantener el formato de tabla. |
| Estados o defectos se distinguen únicamente por color. | Conservar texto, etiquetas e iconografía ya existente; el color es un refuerzo, no el único indicador. |
| Los estilos de T-16 sobrescriben accidentalmente T-15 o impresión. | No editar esos bloques y comprobarlos contra la versión previa al cambio. |
| SVG mantiene colores literales que no coinciden exactamente con los nuevos acentos. | No modificar los SVG ni sus valores; aceptar esa diferencia dentro del alcance CSS-only. |
| El recorrido visual no cubre todas las pantallas. | Usar explícitamente la lista de pantallas de la sección 3 como checklist en escritorio y móvil. |
