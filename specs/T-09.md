## 1. Contexto y motivación breve

La migración de persistencia definida en `docs/adr/ADR-001-persistencia-postgresql.md` (D1, D3, D10, sección 6 paso 5) reemplaza el contrato monolítico `almacen` (Save/Load de colecciones completas) por repositorios por agregado definidos por el consumidor (`internal/service/repositorios.go`, T-06). T-07 y T-08 entregaron el adaptador JSON y la suite de contrato; T-13 ya incorporó el adaptador PostgreSQL en la rama base. T-09 migra los servicios para usar esos contratos y elimina la dependencia directa de `internal/storage` desde el código productivo de `internal/service`, sin cambiar la lógica de negocio.

Los requisitos funcionales no cambian: se conservan las firmas públicas de los métodos de servicio y el comportamiento observable de US-01 a US-05 y US-11. La única excepción aceptada es el cambio de parámetros de los constructores (`almacen` → repositorios), documentada en ADR-001 D1.

## 2. Objetivo

- Migrar `ServicioProyectos` y `ServicioBacklog` para operar sobre `RepositorioProyectos`, `RepositorioIntegrantes` y `RepositorioBacklog`.
- Preservar el comportamiento observable y las aserciones de negocio de los tests existentes, cambiando solo su armado para usar repositorios/fakes.
- Eliminar el acoplamiento de `internal/service` (código no-test) con `internal/storage`.
- Incorporar tests de comportamiento que verifiquen propagación de errores, ausencia de escrituras indebidas, conservación del ID en creación de ítems, no actualización ante validación fallida y no envoltura de errores de dominio.
- Mantener `go vet ./...`, `go test ./...` y cobertura de `internal/service` al 100%.

## 3. Alcance

- `internal/service/proyectos.go`, `internal/service/integrantes.go`, `internal/service/backlog.go`, `internal/service/estimacion.go` y archivos auxiliares relacionados con la migración a repositorios.
- Tests de `internal/service` (`*_test.go`): armado migrado a repositorios/fakes, retarget/eliminación puntual indicada y nuevos tests de comportamiento.
- Nuevo archivo `internal/service/repos_fake_test.go` (`package service`) con fakes en memoria, contadores de escrituras e inyección de errores.
- Conservación/verificación de `TestT09_ServiceNoImportaStorage` en `internal/service/repositorios_test.go` o archivo de tests equivalente.
- Eliminación de elementos obsoletos tras completar la migración (ver R6/Fase 3).

## 4. Exclusiones

- No se modifica `internal/domain`, `internal/storage`, `internal/storage/jsonrepo`, `internal/storage/postgres`, `internal/web`, `cmd/server`, migraciones SQL ni la suite de contrato `internal/service/repotest`.
- No se crean ni modifican archivos `.feature`.
- No se agregan nuevas historias de usuario ni se cambian requisitos funcionales, criterios de aceptación, reglas o escenarios BDD de US-01 a US-05 y US-11.
- No se modifica `.github/workflows/ci.yml` ni `compose.yml`.
- No se implementan repositorios PostgreSQL (T-13) ni infraestructura de base de datos (T-12).

## 6. Reglas de negocio y técnicas

| ID | Regla | CA |
|---|---|---|
| R1 | **Fakes en memoria, sin ciclos.** Los tests de servicio usarán fakes en memoria dentro de `package service`, en `repos_fake_test.go`, con contadores de escrituras e inyección de errores. No deben importar `internal/storage/jsonrepo` ni `internal/service/repotest`, para evitar ciclos de importación. | CA1, CA4 |
| R2 | **Constructores y orquestación migrada.** `ServicioProyectos` se construye con `(proyectos RepositorioProyectos, integrantes RepositorioIntegrantes)` y orquesta `ModificarProyecto` (`Obtener` → validación/dominio → `Actualizar`) y `AgregarIntegrante` (`Existe` → `domain.NuevoIntegrante` → `ListarPorProyecto` + `domain.EsDuplicado` → `Agregar`). `ServicioBacklog` se construye con `(proyectos RepositorioProyectos, backlog RepositorioBacklog)` y orquesta `CrearItem` (`Existe` → `domain.NuevoItemBacklog` → `AgregarItem`) y `EstimarItem` (`Existe` → `ObtenerItem` → estimación de dominio → `ActualizarItem`). | CA1, CA2 |
| R3 | **Conservación de comportamiento y firmas de métodos.** Los métodos públicos existentes conservan firma y comportamiento observable: `ModificarProyecto(id, nombre string, fechaInicio, fechaFin time.Time) (domain.Proyecto, error)`, `AgregarIntegrante(proyectoID, nombre, rol string) (domain.Integrante, error)`, `CrearItem(proyectoID, titulo, descripcion, prioridad string, criterios []string) (domain.ItemBacklog, error)` y `EstimarItem(proyectoID, itemID string, storyPoints int) (domain.ItemBacklog, error)`. | CA2, CA3 |
| R4 | **Tests existentes: mismos nombres y aserciones.** Los tests existentes conservan sus nombres y aserciones de negocio; solo cambia su armado para usar repositorios/fakes. | CA3 |
| R5 | **Propagación de errores de infraestructura.** Los errores de infraestructura devueltos por repositorios se propagan envueltos con `%w` en cada operación (`ModificarProyecto`, `AgregarIntegrante`, `CrearItem`, `EstimarItem`), preservando `errors.Is`/`errors.Unwrap`. Los errores de dominio definidos por el contrato se conservan sin envolver según R7. | CA4 |
| R6 | **No escribir en caminos inválidos o de ausencia/duplicado.** No se invocan operaciones de escritura del repositorio si el proyecto no existe, si hay duplicado de integrante, si falla una validación de dominio o si el ítem no existe según el flujo correspondiente; en particular, `ModificarProyecto` no llama a `Actualizar` si la validación falla. | CA4 |
| R7 | **Errores de dominio sin envolver.** Los errores de dominio devueltos por el dominio o por el contrato de repositorio (`ErrProyectoNoEncontrado`, `ErrItemNoEncontrado`, `ErrIntegranteDuplicado`, errores de validación de dominio) se devuelven sin envolver adicionalmente por el servicio; `errors.Unwrap(err) == nil` cuando el origen es un error de dominio. | CA4 |
| R8 | **ID de ítem conservado.** `CrearItem` conserva y devuelve exactamente el ID devuelto por `RepositorioBacklog.AgregarItem`, sin recalcularlo ni alterarlo. | CA4 |
| R9 | **Eliminaciones y retargets obligatorios.** Eliminar `TestUS11_EstimarItem_BacklogSinArchivo` (cubierto por `repotest`). Retargetear `TestUS11_EstimarItem_MismoIDEnOtroProyecto` para comprobar que el servicio consulta usando el `proyectoID` correcto (alcance por proyecto), sin depender del comportamiento de colección JSON completa. | CA3, CA5 |
| R10 | **Independencia de storage verificada por test.** Mantener `TestT09_ServiceNoImportaStorage` en `internal/service/repositorios_test.go` o archivo de tests equivalente. Debe usar `go/parser` y verificar que ningún `.go` no-test de `internal/service` importe `internal/storage`. | CA6 |
| R11 | **Calidad y cobertura.** `go vet ./...`, `go test ./...` exitosos y cobertura de `internal/service` del 100%. | CA7 |
| R12 | **Implementación por fases con verde continuo.** La implementación se realiza en tres fases y cada commit debe dejar `go test ./...` en verde (ver sección 8). | CA2, CA3, CA5, CA7 |

## 7. Casos límite y condiciones de error

| ID | Caso / condición | Resultado esperado | Reglas |
|---|---|---|---|
| L1 | Error de infraestructura de `RepositorioProyectos.Obtener/Existe/Actualizar`, `RepositorioBacklog.ObtenerItem/AgregarItem/ActualizarItem` o `RepositorioIntegrantes.ListarPorProyecto/Agregar`. | El servicio devuelve error envuelto con `%w` preservando la causa. Si el repositorio devuelve un error de dominio del contrato, aplica R7. | R5, R7 |
| L2 | Proyecto inexistente en cualquier operación. | Se devuelve `domain.ErrProyectoNoEncontrado` sin envolver; no se ejecutan escrituras posteriores del flujo. | R6, R7 |
| L3 | Validación de dominio falla en `ModificarProyecto`, `AgregarIntegrante` o `CrearItem`. | Se devuelve el error de dominio sin envolver; no se llama a `Actualizar`/`Agregar`/`AgregarItem`. | R6, R7 |
| L4 | Integrante duplicado detectado por `domain.EsDuplicado`. | Se devuelve `domain.ErrIntegranteDuplicado` sin envolver; no se llama a `Agregar`. | R6, R7 |
| L5 | Ítem inexistente en `EstimarItem`. | Se devuelve `domain.ErrItemNoEncontrado` (o el error de dominio del contrato) sin envolver; no se llama a `ActualizarItem`. | R6, R7 |
| L6 | `AgregarItem` devuelve un ítem con ID asignado. | `CrearItem` devuelve ese mismo ID/ítem persistido sin alterarlo. | R8 |
| L7 | Backlog sin datos para un proyecto (caso antes cubierto por `TestUS11_EstimarItem_BacklogSinArchivo`). | Cobertura delegada a `repotest` (D10); el test de servicio se elimina en T-09. | R9 |
| L8 | Mismo ID lógico en otro proyecto. | `TestUS11_EstimarItem_MismoIDEnOtroProyecto` verifica que la consulta usa el `proyectoID` correcto. | R9 |
| L9 | Presencia de `internal/storage` en imports de `.go` no-test de `internal/service`. | Falla `TestT09_ServiceNoImportaStorage`. | R10 |

## 8. Fases TDD

Cada fase se implementa siguiendo RED → GREEN → REFACTOR según corresponda, y **cada commit debe dejar `go test ./...` en verde**.

| Fase | Objetivo | Cambios principales | Verificación al finalizar el commit |
|---|---|---|---|
| Fase 1 — Migrar `ServicioProyectos` | Migrar constructor y operaciones de proyectos/integrantes sin romper backlog. | Cambiar constructor de `ServicioProyectos` a `(RepositorioProyectos, RepositorioIntegrantes)`. Migrar `ModificarProyecto` y `AgregarIntegrante` y sus tests. `ServicioBacklog` continúa usando `almacen`. Crear/usar fakes necesarios en `repos_fake_test.go` (solo lo requerido, manteniendo verde). | `go test ./...` verde |
| Fase 2 — Migrar `ServicioBacklog` | Completar migración de backlog/estimación. | Cambiar constructor de `ServicioBacklog` a `(RepositorioProyectos, RepositorioBacklog)`. Migrar `CrearItem`, `EstimarItem` y sus tests. Adaptar armado restante para eliminar dependencia de `almacen` en tests de backlog. | `go test ./...` verde |
| Fase 3 — Limpieza | Eliminar infraestructura obsoleta y cerrar independencia/cobertura. | Eliminar `almacen`, `proyectoRegistrado`, `integranteRegistrado`, `itemRegistrado`, `verificarProyectoExistente`, `cargarColeccionBacklog` y referencias muertas. Aplicar eliminaciones/retargets de tests (R9). Asegurar `TestT09_ServiceNoImportaStorage` y nuevos tests de comportamiento. | `go vet ./...` y `go test ./...` verdes; cobertura `internal/service` 100% |
