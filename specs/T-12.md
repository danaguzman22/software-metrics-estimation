# T-12 — Infraestructura PostgreSQL

- **Issue:** #45
- **Tipo:** técnica / infraestructura
- **Estado:** Implementada
- **Rama:** `feature/T-12-infraestructura-postgresql` → PR a `migracion/postgresql`
- **Decisiones del ADR-001:** D6 (esquema inicial) y D8 (pgx v5 y goose)
- **Depende de:** ninguna
- **Habilita:** T-13 (#46), repositorios PostgreSQL

## 1. Contexto

La migración de persistencia necesita una conexión PostgreSQL reutilizable y una
primera migración versionada antes de que el servidor atienda tráfico. La
aplicación requiere PostgreSQL 13 o superior por el uso de
`gen_random_uuid()` nativo.

Esta tarea es de infraestructura, sin comportamiento de usuario; siguiendo la
convención de T-07, no genera un archivo `.feature`. La trazabilidad se verifica
con tests Go sobre la inicialización, la migración embebida y, cuando hay una
base disponible, su aplicación real.

## 2. Alcance

**Incluye:** dependencias pgx v5 y goose; conexión mediante `pgxpool`;
migración goose embebida en `migrations/` con el esquema D6; e inicialización
de `cmd/server` desde `DATABASE_URL`.

**No incluye:** repositorios PostgreSQL (T-13), cambios funcionales, ni cambios
al esquema fuera del DDL acordado en D6. El repositorio todavía no tiene un
servidor HTTP ni rutas en `internal/web`; esta tarea deja la inicialización de
la base como bootstrap y cualquier listener futuro debe iniciarse después de
`ConnectAndMigrate`.

## 3. Reglas

- **R1 — Dependencias y conexión:** usar pgx v5 con `pgxpool`, sin ORM. La
  inicialización debe validar conectividad y devolver errores explícitos.
- **R2 — Migración versionada e inmutable:** incluir el DDL de D6 como primera
  migración goose dentro de `migrations/` y embebida mediante `go:embed`.
- **R3 — Esquema:** crear `proyectos`, `integrantes` e `items_backlog` con las
  columnas, claves y restricciones de D6, además del índice único de integrantes.
  Las fechas de proyecto son `date`; los criterios son
  `text[] NOT NULL DEFAULT '{}'`; la clave primaria de ítem es
  `(proyecto_id, numero)`.
- **R4 — Estado de proyecto:** el CHECK admite exactamente los estados
  existentes en el dominio: `Planificado`, `En curso` y `Finalizado`.
- **R5 — Arranque:** `cmd/server` requiere `DATABASE_URL`, conecta y aplica
  migraciones al arrancar, con un timeout de 30 segundos para el bootstrap. Un
  error de configuración, conexión o migración debe impedir el arranque y
  comunicarse explícitamente. Cualquier servidor HTTP que se incorpore después
  debe arrancar una vez finalizada esta etapa.
- **R6 — Compatibilidad:** `go build ./...` y `go test ./...` deben pasar; la
  migración debe aplicarse sobre una base vacía PostgreSQL 13+.

## 4. Criterios de aceptación

- **CA1:** `go.mod` incluye pgx v5 (incluido `pgxpool`) y goose.
- **CA2:** la primera migración Goose embebida crea las tres tablas según D6,
  incluyendo UUID textual por defecto, fechas `date`, checks, FKs, índice
  único de integrantes y PK compuesta de backlog. No se agrega un índice
  redundante sobre `(proyecto_id, numero)`.
- **CA3:** el estado CHECK de `proyectos` coincide con los literales del
  dominio.
- **CA4:** el arranque lee `DATABASE_URL` y aplica migraciones antes de
  completar su bootstrap, dentro de un timeout de 30 segundos.
- **CA5:** `go build ./...` y `go test ./...` pasan; la migración funciona sobre
  una base vacía PostgreSQL 13 o superior.
