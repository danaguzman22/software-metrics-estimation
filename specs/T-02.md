## Fuente única de requisitos

> Esta tarea provee un almacenamiento genérico en archivos JSON, desacoplado del dominio, para guardar y recuperar datos de la aplicación.
>
> Fuente de verdad: `internal/storage/storage.go` y `internal/storage/storage_test.go`.

Esta spec describe únicamente el comportamiento ya implementado y verificado por los tests. No agrega reglas de negocio, funcionalidades ni contratos nuevos. Lo ambiguo o no cubierto se lista en **Decisiones de diseño** y en **Decisiones pendientes de confirmación**.

## 1. Descripción

El paquete `internal/storage` ofrece un almacenamiento genérico que serializa valores en archivos JSON dentro de un directorio base. Cada nombre lógico se traduce en un archivo `<name>.json`. Expone operaciones para crear el almacenamiento, guardar (`Save`) y cargar (`Load`), con errores identificables para archivo inexistente, JSON corrupto y nombre inválido.

No contiene lógica de dominio. Según `AGENTS.md`, la lógica de negocio vive en `internal/domain`; esta tarea solo provee persistencia.

## 2. Objetivo

Proveer un almacenamiento genérico en archivos JSON, desacoplado del dominio, para guardar y recuperar datos de la aplicación.

## 3. Alcance

### Incluido

- Creación del almacenamiento con un directorio base, creando el directorio si no existe (incluidos directorios anidados).
- Rechazo de directorio base vacío o compuesto únicamente por espacios.
- Guardado de valores serializables en `<name>.json`.
- Carga de valores desde `<name>.json`.
- Sobrescritura de un archivo existente al guardar con el mismo nombre.
- Validación de nombres lógicos.
- Errores identificables: `ErrNotFound`, `ErrCorrupt`, `ErrInvalidName`.
- Escritura mediante archivo temporal y renombrado (decisión pendiente de aprobación de Dana).

### Fuera de alcance

- Lógica de negocio del dominio.
- Búsqueda por ID y persistencia de cambios de US-02 (ver nota de pendiente en la sección 13).
- Concurrencia, bloqueos, transacciones, versionado, migraciones o cifrado.
- Interfaz web o de usuario.
- Formato de fechas, validaciones de dominio o reglas de unicidad.
- Definición de un contrato de almacenamiento específico para US-02.

No se agregan funcionalidades que no estén implementadas y verificadas por los tests.

## 4. Entradas

| Campo | Tipo | Obligatorio | Validación | Origen |
|---|---|---|---|---|
| `dir` | string | Sí | No vacío ni compuesto únicamente por espacios (`strings.TrimSpace`). Si no existe, se crea con `os.MkdirAll`. | `NewJSONStore` |
| `name` | string | Sí | No vacío, distinto de `.` y `..`, y sin `/` ni `\`. | `path` / `Save` / `Load` |
| `v` (Save) | any | Sí | Debe ser serializable a JSON. | `Save` |
| `v` (Load) | any | Sí | Debe ser un puntero para que `json.Unmarshal` complete el destino. | `Load` |

## 5. Salidas esperadas

| Operación | Salida esperada |
|---|---|
| `NewJSONStore(dir)` | Almacenamiento listo para usar; crea el directorio base si no existe. |
| `Save(name, v)` | Crea o sobrescribe `<dir>/<name>.json` con el valor serializado. |
| `Load(name, v)` | Completa el destino `v` con el contenido de `<dir>/<name>.json`. |
| Error de directorio vacío | Error descriptivo, sin crear almacenamiento. |
| Error de nombre inválido | `ErrInvalidName`. |
| Error de archivo inexistente | `ErrNotFound`. |
| Error de JSON malformado | `ErrCorrupt`. |
| Error de destino no puntero | Error de JSON distinto de `ErrCorrupt`. |
| Error de serialización | Error descriptivo; no se crea archivo. |

Nota: la implementación actual serializa con `json.MarshalIndent` (indentación de dos espacios). Los tests no verifican la indentación; se documenta como detalle de implementación, no como regla de negocio.

## 7. Validaciones

| ID | Validación | Resultado esperado | Regla |
|---|---|---|---|
| V1 | Directorio base vacío o compuesto únicamente por espacios | Error descriptivo | R6 |
| V2 | Nombre vacío, `.`, `..`, o con `/` o `\` | `ErrInvalidName` en `Save` y `Load` | R7 |
| V3 | Valor no serializable en `Save` | Error descriptivo; no se crea archivo | R11 |
| V4 | Destino de `Load` que no es puntero | Error de JSON distinto de `ErrCorrupt` | R10 |

No se agregan validaciones adicionales (por ejemplo, longitud del nombre, caracteres permitidos, nombres compuestos únicamente por espacios, unicidad o concurrencia), porque no están implementadas ni verificadas por los tests.

## 8. Casos límite

- Directorio base inexistente y anidado: se crea (R5, CA5).
- Directorio base vacío o compuesto únicamente por espacios: devuelve error (R6, CA6).
- Sobrescribir un archivo existente: el último valor guardado prevalece y no quedan temporales (R3, R4, CA7).
- Valor no serializable (por ejemplo, un canal): devuelve error y no deja archivos (R11, CA8).
- Nombres con separadores de ruta o `..` (path traversal): se rechazan con `ErrInvalidName` (R7, CA4).
- Cargar un archivo inexistente: `ErrNotFound` (R8, CA2).
- Cargar JSON malformado: `ErrCorrupt` (R9, CA3).
- Cargar con destino no puntero: error distinto de `ErrCorrupt` (R10, CA9).
- Nombre compuesto únicamente por espacios: **no está cubierto por los tests actuales**. La implementación actual lo acepta como nombre no vacío. Queda dentro de la decisión pendiente de validación de nombres (sección 13).
- Fallo durante la escritura o el renombrado: la implementación intenta limpiar el temporal, pero no hay test que lo verifique. Queda dentro de la decisión pendiente de escritura atómica (sección 13).

## 9. Condiciones de error

| Condición | Error | Verificación |
|---|---|---|
| Directorio base vacío o compuesto únicamente por espacios | Error descriptivo (no es uno de los errores nombrados) | `TestNewJSONStore_EmptyDir` |
| Nombre inválido | `ErrInvalidName` | `TestSave_InvalidName` |
| Archivo inexistente al cargar | `ErrNotFound` | `TestLoad_NotFound` |
| JSON malformado al cargar | `ErrCorrupt` | `TestLoad_CorruptJSON` |
| Destino de carga que no es puntero | Error de JSON distinto de `ErrCorrupt` | `TestLoad_NonPointerTarget_NoEsCorrupt` |
| Valor no serializable al guardar | Error descriptivo; no se crea archivo | `TestSave_UnmarshalableValue` |

Los errores nombrados se verifican con `errors.Is` en los tests.

## 10. Comportamiento esperado

### Caso normal

1. Se crea el almacenamiento con un directorio válido.
2. Se guarda un valor serializable con un nombre válido.
3. Se carga el mismo nombre en un destino puntero.
4. Se obtiene el mismo valor guardado.

Resultado: round trip exitoso (R1, R2, CA1).

### Casos alternativos / de error

- Nombre inválido: `ErrInvalidName` (R7, V2, CA4).
- Archivo inexistente: `ErrNotFound` (R8, CA2).
- JSON malformado: `ErrCorrupt` (R9, CA3).
- Destino no puntero: error distinto de `ErrCorrupt` (R10, V4, CA9).
- Directorio base vacío: error descriptivo (R6, V1, CA6).
- Valor no serializable: error y sin archivo (R11, V3, CA8).

### Casos límite

- Directorio base inexistente y anidado: se crea (R5, CA5).
- Sobrescritura de un archivo existente: prevalece el último valor y solo queda `<name>.json` (R3, R4, CA7).
- Nombre compuesto únicamente por espacios: no cubierto por tests; **PENDIENTE DE DECIDIR** (sección 13).
- Fallo entre escritura y renombrado: no cubierto por tests; **PENDIENTE DE DECIDIR** (sección 13).

## 13. Decisiones de diseño

| Decisión | Estado |
|---|---|
| (a) Escritura atómica | Pendiente de aprobación de Dana |
| (b) Nombres de errores `ErrNotFound`, `ErrCorrupt`, `ErrInvalidName` | Pendiente de aprobación de Dana |
| (c) Validación de nombres | Pendiente de aprobación de Dana |

### (a) Escritura atómica

**Pendiente de aprobación de Dana.** La implementación escribe en un archivo temporal en el mismo directorio y luego lo renombra (`os.CreateTemp` + `os.Rename`), y elimina el temporal ante error. Los tests verifican que no quedan temporales tras una sobrescritura exitosa y que un valor no serializable no deja archivos, pero no simulan un fallo entre escritura y renombrado. Queda pendiente que Dana apruebe este mecanismo como contrato.

### (b) Nombres de errores `ErrNotFound`, `ErrCorrupt`, `ErrInvalidName`

**Pendiente de aprobación de Dana.** El paquete expone tres errores nombrados con esos identificadores y mensajes en español. Los tests usan `errors.Is` para verificarlos. Queda pendiente que Dana apruebe los nombres y el contrato de errores.

### (c) Validación de nombres

**Pendiente de aprobación de Dana.** La implementación considera inválidos los nombres `""`, `.`, `..` y los que contienen `/` o `\`. No recorta ni valida espacios internos o externos del nombre; por ejemplo, un nombre compuesto únicamente por espacios no es rechazado por la implementación actual y no está cubierto por tests. Queda pendiente que Dana apruebe la regla de validación de nombres.

Pendiente: contrato de almacenamiento para US-02 (búsqueda por ID y persistencia de cambios), a definir con Dana
