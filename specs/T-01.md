# T-01 — Estructura del proyecto Go, go.mod y CI con `go test`

- **Issue:** #12
- **Tipo:** Historia técnica
- **Prioridad:** Alta
- **Story Points:** 3
- **Sprint planificado:** S1
- **Estado de la especificación:** borrador para revisión de la persona

## 1. Objetivo

Dejar armada la base técnica del repositorio para que el equipo pueda desarrollar sobre un módulo Go único, con una separación explícita de capas y con verificación automática de compilación y pruebas en GitHub Actions.

T-01 **no implementa funcionalidades de negocio**: solo prepara el esqueleto del proyecto, el módulo, la estructura de paquetes, el punto de entrada mínimo y el workflow de integración continua.

## 4. Reglas de negocio (técnicas)

> En T-01 las “reglas de negocio” son reglas técnicas verificables. No se agregan criterios de aceptación distintos de CA1, CA2 y CA3.

### R1 — Compilación del repositorio

El repositorio debe compilar con `go build ./...` sin errores.

- **Cubre:** CA1.
- **Verificación:** paso `go build ./...` del workflow de CI y ejecución local del mismo comando.

### R2 — Ejecución de pruebas en GitHub Actions

GitHub Actions debe ejecutar `go test ./... -cover` en cada push a cualquier rama y en cada pull_request hacia `develop` o `main`.

- **Cubre:** CA2.
- **Verificación:** configuración del workflow (eventos `push` y `pull_request`) y ejecución registrada en GitHub Actions.

### R3 — Separación entre lógica de negocio y capa web

La lógica de negocio debe vivir en `internal/domain`, separada de la capa web. En particular, `internal/domain` no debe importar `internal/web`.

- **Cubre:** CA3.
- **Verificación:** test Go estructural que inspecciona los imports reales de `internal/domain` y falla si encuentra `internal/web` o `net/http`. `net/http` es una guarda técnica de desacople de la capa web; esta guarda adicional no constituye un criterio de aceptación nuevo.

### R4 — Pasos obligatorios del workflow

El workflow de CI debe ejecutar, como mínimo, `go build ./...` y `go test ./... -cover`.

- **Cubre:** CA1 y CA2.
- **Verificación:** contenido del workflow y logs de ejecución del run en GitHub Actions.

### R5 — Configuración del workflow

El workflow debe vivir en `.github/workflows/ci.yml`, ejecutarse en `ubuntu-latest` y configurar Go con `setup-go` usando `go-version-file` apuntando a `go.mod`, sin fijar una versión distinta en el workflow.

- **Cubre:** base de CA2.
- **Verificación:** contenido del workflow y logs del run en GitHub Actions, donde la versión configurada debe coincidir con la declarada en `go.mod` y el runner debe ser `ubuntu-latest`.

## 5. Restricciones

- El archivo `go.mod` debe declarar el módulo `github.com/danaguzman22/software-metrics-estimation` y la directiva `go 1.24`. Verificación reproducible: `go list -m`, `go build ./...` y revisión de `go.mod`.
- La estructura debe incluir los paquetes `cmd/server`, `internal/domain`, `internal/service`, `internal/storage` e `internal/web`. Verificación reproducible: `go build ./...`, `go list ./...` y el smoke test de `internal/domain`.
- No se implementa lógica de negocio en T-01.
- `cmd/server/main.go` debe ser mínimo: sin rutas, sin UI y sin lógica de negocio.
- No se agregan criterios de aceptación nuevos: se mantienen CA1, CA2 y CA3 del issue.
- Los archivos `.feature` son documentales y no se ejecutan con godog; se mapean a tests Go o verificaciones de CI por tag `@CA`.
- La dependencia permitida `web → service/domain` es una nota de arquitectura, **no** un criterio de aceptación adicional de T-01.
- El único criterio estructural obligatorio en BDD es: `internal/domain` no importa `internal/web`.
- Todo el código de la solución debe ser Go; HTML/CSS/JS no aplica a T-01.
- La persona es quien crea la rama, hace commits, push, Pull Request y merge; la IA no toca `main` ni `develop`.
- La cobertura se ejecuta con `-cover`, pero T-01 no define umbral mínimo de cobertura.
- El workflow de CI se ubica en `.github/workflows/ci.yml` y se ejecuta en el runner `ubuntu-latest`.
- T-01 no configura branch protection para `develop` ni `main`.
- `docs/` debe existir con un archivo placeholder; su contenido definitivo no forma parte de T-01.

## 6. Casos límite

| Caso límite | Resultado esperado |
|---|---|
| Push a una rama distinta de `develop` o `main` (por ejemplo, `feature/T-01-estructura-proyecto-go`). | El workflow se dispara igual porque la regla es push a todas las ramas. |
| Pull request hacia `develop` o `main`. | El workflow se dispara por la regla de pull_request. |
| Pull request hacia una rama distinta de `develop` o `main`. | El workflow no se dispara; no es un requisito de T-01. |
| `internal/domain` existe pero todavía no tiene lógica de negocio. | `go build ./...` y el smoke test pasan; el paquete compila. |
| Paquetes sin archivos de test. | `go test ./... -cover` termina correctamente y reporta cobertura; no hay umbral que haga fallar el run. |
| Cobertura de 0 % en paquetes sin tests. | No se considera fallo de T-01; el issue solo pide ejecutar `-cover`. |
| Toolchain local Go 1.27.3 frente a `go 1.24` declarado. | La compilación local es compatible; CI usa la versión declarada en `go.mod`. |
| `cmd/server/main.go` mínimo, sin rutas ni UI. | `go build ./...` pasa; T-01 no valida comportamiento en ejecución. |
| Push o merge a `develop` o `main`. | El workflow se dispara por la regla de push a todas las ramas. |

| Condición de error | Efecto esperado | Regla / CA afectada |
|---|---|---|
| `go build ./...` falla por un error de compilación. | El workflow queda en rojo; CA1 no se cumple. | R1 / CA1 |
| `go test ./... -cover` falla porque un test no pasa. | El workflow queda en rojo; CA2 no se cumple. | R2 / CA2 |
| `internal/domain` importa `internal/web`. | El test estructural falla; CA3 no se cumple. | R3 / CA3 |
| `internal/domain` importa `net/http`. | Falla la guarda técnica de desacople del test estructural; no se interpreta como un incumplimiento independiente del criterio literal CA3. | R3 (guarda técnica) |
| El workflow no existe, está mal formado o no se dispara en push. | No hay verificación automática en cada push; CA2 no se cumple. | R2 / CA2 |
| El workflow ejecuta `go test` sin `-cover`. | Se incumple el paso acordado de CI. | R4 |
| El workflow omite `go build ./...`. | Se incumple el paso acordado de CI. | R4 |
| El workflow fija una versión de Go distinta de la declarada en `go.mod`. | Se incumple la configuración acordada de CI. | R5 |
| `go.mod` no existe, tiene un módulo inválido o una directiva distinta de `go 1.24`. | La compilación o la verificación del módulo falla. | Restricción de módulo / CA1 |
| Falta alguno de los paquetes de la estructura objetivo. | `go build ./...` o `go list ./...` no refleja la estructura esperada. | Restricción de estructura |
| `cmd/server/main.go` contiene rutas, UI o lógica de negocio. | Se incumple el alcance de T-01; requiere corrección en revisión. | Restricción de alcance |
| Un escenario BDD no tiene tag `@CA1`, `@CA2` o `@CA3`. | Queda un hueco de trazabilidad; requiere corrección. | Trazabilidad |

## 8. Criterios de aceptación

### CA1 — El repositorio compila con `go build ./...`

El repositorio debe compilar sin errores usando `go build ./...`. La verificación completa de compilación del repositorio es `go build ./...`, tanto localmente como en CI.

- **Verificación principal:** paso `go build ./...` en CI y ejecución local.
- **Prueba complementaria Go:** smoke test de compilación/paquete en `internal/domain` (nombre propuesto: `TestDomainPackageCompiles`). No reemplaza la verificación completa con `go build ./...`.

### CA2 — `go test ./...` corre en GitHub Actions en cada push

En cada push, GitHub Actions debe ejecutar las pruebas. La ejecución acordada es `go test ./... -cover`, que incluye `go test ./...`.

- **Verificación:** workflow de GitHub Actions con eventos `push` (todas las ramas) y `pull_request` hacia `develop` y `main`; revisión del run en GitHub Actions.
- **Nota:** CA2 se verifica por CI, no por un test Go.

### CA3 — La lógica de negocio vive en un paquete separado de la capa web

La lógica de negocio debe residir en `internal/domain`, separada de `internal/web`. La verificación estructural obligatoria es que `internal/domain` no importa `internal/web`.

- **Verificación:** test Go estructural (nombre propuesto: `TestDomainDoesNotImportWeb`) en `internal/domain`, que inspecciona los imports reales del paquete y falla si encuentra `internal/web` o `net/http`.
- **Nota:** `net/http` es una guarda técnica adicional del mismo test, no un criterio de aceptación adicional.

## 9. Trazabilidad

### 9.1 Matriz criterio → escenario → verificación

| Criterio | Escenario BDD | Verificación | Paquete / artefacto |
|---|---|---|---|
| CA1 | `features/T-01.feature` → `@CA1` | CI: `go build ./...` (verificación completa); test Go smoke complementario `TestDomainPackageCompiles` (propuesto, no reemplaza `go build ./...`). | `go.mod`, `cmd/server`, `internal/{domain,service,storage,web}` |
| CA2 | `features/T-01.feature` → `@CA2` | CI: workflow en push y pull_request; ejecución de `go build ./...` y `go test ./... -cover`. | Workflow de GitHub Actions |
| CA3 | `features/T-01.feature` → `@CA3` | Test Go estructural `TestDomainDoesNotImportWeb` (propuesto). | `internal/domain` |

### 9.2 Tests automatizados Go vs. verificaciones de CI

| Tipo de verificación | Alcance | Criterio |
|---|---|---|
| Test Go smoke `TestDomainPackageCompiles` (propuesto) | Prueba complementaria: comprueba que `internal/domain` compila como paquete. No reemplaza `go build ./...`. | CA1 |
| Test Go estructural `TestDomainDoesNotImportWeb` (propuesto) | Inspecciona los imports reales de `internal/domain` y falla si encuentra `internal/web` o `net/http`. | CA3 |
| Workflow de GitHub Actions | Se dispara en push a todas las ramas y en pull_request hacia `develop`/`main`; ejecuta `go build ./...` y `go test ./... -cover`. | CA1 y CA2 |
| Revisión humana | Verifica alcance de `main.go`, nombre/ubicación del workflow, `go-version-file` y ausencia de criterios inventados. | Restricciones y R4/R5 |

### 9.3 Flujo TDD previsto

1. **RED:** crear los tests Go smoke y estructural; deben fallar antes de la implementación.
2. **GREEN:** crear `go.mod`, estructura de paquetes, `cmd/server/main.go`, placeholders y workflow hasta que `go build ./...` y `go test ./... -cover` pasen.
3. **REFACTOR:** ordenar paquetes y documentación sin cambiar el comportamiento verificado.
