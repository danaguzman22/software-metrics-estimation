## Fuente única de requisitos

> Tarea técnica: formulario y listado de integrantes por proyecto (hoy se cargan
> por SQL), y aviso en Planning Poker cuando el proyecto no tiene integrantes.
> Surge de la retrospectiva del Sprint 2.
>
> Issue #87.

Esta spec no agrega requisitos fuera de esa fuente, con una excepción explícita:
las **decisiones DECIDIDAS 1–5** fueron confirmadas por la persona para cerrar el
alcance y el comportamiento de la tarea. Los detalles de rutas, contrato web,
plantilla, textos, casos de prueba y estrategia de verificación se proponen como
**DERIVADAS 6–13** y se listan en la sección 4 para revisión.

La tarea nace de la retrospectiva del Sprint 2: hoy los integrantes solo se
cargan por SQL y no hay pantalla para registrarlos; además, Planning Poker
muestra un desplegable vacío cuando el proyecto no tiene integrantes
(`docs/retrospectivas/sprint-2.md`, acción del Sprint 3). US-03 ya implementó el
dominio y el servicio de alta y listado de integrantes.

## 1. Contexto

- `internal/domain/integrante.go` define `Integrante{Nombre, Rol}`,
  `NuevoIntegrante(nombre, rol)` y `EsDuplicado`. El dominio recorta espacios,
  valida nombre, luego rol y luego duplicado (ignorando mayúsculas y espacios
  extremos), y define los errores exactos:
  - `ErrNombreIntegranteVacio`: "el nombre del integrante no puede estar vacío".
  - `ErrRolIntegranteVacio`: "el rol del integrante no puede estar vacío".
  - `ErrIntegranteDuplicado`: "el integrante ya está registrado en el proyecto".
- `internal/service/integrantes.go` ya expone
  `ListarIntegrantes(proyectoID string) ([]domain.Integrante, error)` y
  `AgregarIntegrante(proyectoID, nombre, rol string) (domain.Integrante, error)`.
  Ambos verifican la existencia del proyecto y devuelven
  `domain.ErrProyectoNoEncontrado` si no existe. El listado respeta el orden de
  inserción devuelto por el repositorio.
- `internal/web/aplicacion.go` ya declara `ListarIntegrantes` en
  `ServicioProyectosWeb`, pero no declara el alta ni registra rutas de
  integrantes.
- `internal/web/poker.go` lista integrantes solo cuando existe una ronda; si el
  proyecto no tiene integrantes, los `<select name="integrante">` quedan vacíos y
  el envío termina en el error de nombre vacío del dominio.
- La tarea es de capa web: no requiere cambios de dominio, servicio,
  repositorios ni migraciones.

## 2. Alcance

**Incluye:**

- Página por proyecto con listado de integrantes y formulario de alta en
  `GET /proyectos/{id}/integrantes`.
- Alta de integrante en `POST /proyectos/{id}/integrantes`, reutilizando
  `ServicioProyectos.AgregarIntegrante` sin duplicar reglas.
- Enlace "Ver integrantes" en el detalle del proyecto, sin quitar los enlaces
  existentes.
- Aviso claro en Planning Poker cuando el proyecto no tiene integrantes, con
  enlace a la página de integrantes, sin desplegables vacíos y sin cambiar las
  reglas de Poker.
- Tests de capa web, test de composición de rutas en `cmd/server`, evidencias
  RED, GREEN y REFACTOR.

**No incluye:**

- Modificar o eliminar integrantes.
- Catálogo de roles, autenticación, permisos, paginación o JavaScript dinámico.
- Cambios en `internal/domain`, `internal/service`, `internal/storage`,
  migraciones, `cmd/server/main.go` ni `compose.yml`.
- Cambios en las reglas, estados, votos, revelado o acuerdo de Planning Poker.
- Cambios en la navegación base ni eliminación de enlaces existentes.
- Reportes, PDF, dashboard, defectos, esfuerzo o métricas.

## 3. Entradas y salidas

### Entradas

| Entrada | Descripción | Origen |
|---|---|---|
| `id` (ruta) | ID del proyecto al que pertenecen los integrantes. | Issue #87, D1 |
| `nombre` (formulario) | Nombre del integrante. Se envía tal como lo escribe la persona; el dominio lo recorta y valida. | D2, D3 |
| `rol` (formulario) | Rol del integrante, texto libre. Se envía tal como lo escribe la persona; el dominio lo recorta y valida. | D2, D3 |

El formulario usa `application/x-www-form-urlencoded`. La web no recorta,
normaliza, compara duplicados ni valida longitud o formato: todo eso pertenece
al dominio y al servicio ya implementados en US-03.

### Salidas

| Situación | Salida esperada |
|---|---|
| `GET` con proyecto existente | HTTP 200 con listado (posiblemente vacío) y formulario. |
| `GET` con proyecto inexistente | HTTP 404 con el mensaje del dominio `domain.ErrProyectoNoEncontrado`. |
| `POST` con alta válida | HTTP 303 a `GET /proyectos/{id}/integrantes`; sin cuerpo de respuesta. |
| `POST` con nombre vacío, rol vacío o duplicado | HTTP 422 con la misma página, el mensaje exacto del dominio y los valores ingresados conservados. |
| `POST` con proyecto inexistente | HTTP 404 con el mensaje del dominio; no se registra nada. |
| Método distinto de `GET`/`POST` en la ruta | HTTP 405 automático del `ServeMux`; el handler no se ejecuta. |
| Error de infraestructura | HTTP 500 con `mensajeErrorInfraestructura` ("Ocurrió un error inesperado. Intentá nuevamente."); el detalle solo va al log. |
| Planning Poker sin integrantes | Aviso visible con enlace a `/proyectos/{id}/integrantes`; sin formularios que dependan de un desplegable de integrantes. |

## 5. Reglas

Cada regla es verificable con tests.

- **R1 — Rutas y métodos.** Solo se registran `GET` y `POST` en
  `/proyectos/{id}/integrantes`. Cualquier otro método sobre esa ruta responde
  405 sin ejecutar el handler.
- **R2 — Página de integrantes.** `GET` obtiene `id` de la ruta, llama a
  `ListarIntegrantes(id)` y renderiza `integrantes` con HTTP 200. Si el servicio
  devuelve `domain.ErrProyectoNoEncontrado`, responde 404 con ese mensaje; ante
  cualquier otro error, responde 500 genérico y registra el detalle en el log.
- **R3 — Alta y redirección.** `POST` parsea el formulario y llama a
  `AgregarIntegrante(id, nombre, rol)`. Si el alta es exitosa, responde 303 con
  `Location: /proyectos/{id}/integrantes` y sin cuerpo. Si `ParseForm` falla,
  responde 422 con "No se pudo leer el formulario." y el formulario vacío.
- **R4 — Errores de validación.** Solo `domain.ErrNombreIntegranteVacio`,
  `domain.ErrRolIntegranteVacio` y `domain.ErrIntegranteDuplicado` se traducen a
  HTTP 422 con la misma página, el mensaje exacto del dominio y los valores
  ingresados. La web no valida ni normaliza por su cuenta.
- **R5 — Proyecto inexistente.** En `GET` y en `POST`, un
  `domain.ErrProyectoNoEncontrado` responde 404 con el mensaje del dominio y no
  registra nada. La existencia la verifica el servicio de US-03.
- **R6 — Errores de infraestructura.** Cualquier otro error responde 500 con el
  mensaje genérico de la aplicación; el detalle se registra solo en el log y
  nunca se muestra en el cuerpo.
- **R7 — Sin reglas duplicadas ni recálculos.** La web copia nombre y rol del
  `domain.Integrante` devuelto por el servicio. No recorta espacios, no compara
  duplicados, no ordena la lista, no calcula nada y no conoce las reglas de
  US-03.
- **R8 — Escape de salida.** Se usa `html/template` sin `template.HTML`. Los
  nombres y roles se escapan tanto en la tabla como en los atributos `value` del
  formulario. Un nombre con `<script>` no se interpreta como HTML.
- **R9 — Listas vacías.** En Go, la decisión de lista vacía se hace con
  `len(integrantes) == 0`; no se compara con `nil`. En las plantillas se usa
  `len`/verdad de la colección y se muestra el estado vacío correspondiente.
- **R10 — Navegación.** El detalle del proyecto conserva "Ver backlog", "Ver
  sprints", "Ver defectos", "Ver dashboard" y "Ver reporte", y agrega "Ver
  integrantes" apuntando a `/proyectos/{id}/integrantes`. No se modifica la
  navegación base.
- **R11 — Planning Poker sin integrantes.** La página de Poker siempre obtiene
  los integrantes del proyecto. Si no hay, muestra el aviso con enlace a la
  página de integrantes y no renderiza los formularios de votar, revelar ni
  acordar. Los botones de inicio/nueva ronda y las llamadas y reglas del servicio
  de Poker no cambian. Un error al listar integrantes se resuelve con el
  `responderErrorPoker` existente (404 o 500 según corresponda).
- **R12 — Contrato y dobles de prueba.** `ServicioProyectosWeb` incluye el alta;
  los dobles de prueba que implementan el contrato se actualizan para compilar.
  El test de composición de `cmd/server` verifica las rutas nuevas sin conectar
  a PostgreSQL.
- **R13 — Alcance técnico.** No se modifica el dominio, el servicio, los
  repositorios, las migraciones, `cmd/server/main.go`, `compose.yml` ni las
  reglas de Poker. La lógica de negocio sigue viviendo en `internal/domain`.

## 7. Comportamiento esperado

### Caso normal

1. La persona entra al detalle del proyecto y elige "Ver integrantes".
2. La página muestra el ID del proyecto, la tabla de integrantes (o el estado
   vacío) y el formulario con "Nombre" y "Rol".
3. Completa ambos campos y envía "Registrar integrante".
4. La web delega en `AgregarIntegrante`; el dominio recorta espacios y valida.
5. Si el alta es válida, responde 303 al listado y el integrante aparece en la
   tabla, en el orden devuelto por el servicio.

### Casos alternativos y de error

- Nombre vacío o solo espacios: 422 con "el nombre del integrante no puede estar
  vacío"; se conserva el rol ingresado; no se agrega nada.
- Rol vacío o solo espacios: 422 con "el rol del integrante no puede estar
  vacío"; se conserva el nombre ingresado; no se agrega nada.
- Nombre duplicado en el proyecto (ignorando mayúsculas y espacios extremos):
  422 con "el integrante ya está registrado en el proyecto"; se conservan ambos
  valores; no se agrega nada.
- Proyecto inexistente en `GET` o `POST`: 404 con el mensaje del dominio.
- Error de infraestructura al listar o agregar: 500 con el mensaje genérico; el
  detalle solo en el log.
- Formulario ilegible: 422 con "No se pudo leer el formulario.".
- Método distinto de `GET`/`POST`: 405 sin ejecutar el handler.
- Poker sin integrantes: aviso con enlace a la página de integrantes; no se
  muestran formularios de votar, revelar ni acordar.

## 8. Casos límite

- Proyecto sin integrantes: página 200 con "El proyecto no tiene integrantes" y
  formulario disponible.
- Primer integrante: alta normal; no hay integrantes previos para comparar.
- Varios integrantes: se muestran todos, en el orden del servicio.
- Nombre o rol con espacios externos: el dominio los recorta; la web no.
- Nombre o rol solo con espacios: error de dominio con 422.
- Nombre con espacios internos: válido; no se altera.
- Nombre con mayúsculas distintas de uno existente: duplicado según el dominio;
  la web muestra el error exacto.
- Nombre con markup (`<script>alert(1)</script>`): se muestra escapado; no se
  interpreta como HTML.
- Nombre o rol muy largos: no hay límite de longitud definido; se muestran tal
  como los devuelve el dominio.
- Proyecto inexistente en `GET` y en `POST`: 404; no se crea nada.
- Error al listar integrantes después de un error de validación: 404 si el
  proyecto ya no existe; 500 genérico ante otro error.
- Poker sin integrantes con ronda abierta, revelada o sin rondas: aviso visible;
  no hay `<select name="integrante">` vacío.
- Poker con integrantes: se conservan los formularios y el comportamiento
  existente de US-12/US-13.
